## What this closes

### Sprint-4 deferred-item list — all four addressed

1. **`provider_event_id` source** — was body+signature hash; now the marketplace-asserted Shopee `event_id`. Replays of the same logical event (semantically identical with any byte drift) collide on UNIQUE → first-write-only outbox.
2. **Outbox event_type** — was placeholder string; now `typeof(OrderImportedV1).AssemblyQualifiedName!` with per-line internal SKUs resolved via `IProductMappingService`. Sprint-4 U4's `OutboxRouteRegistry` routes as `SendKind.Send` → Outbound's `OrderImportedConsumer` is the destination.
3. **Scale-gate harness bodies** — three `[Fact]` tests in tree, `Category=Load`, using `TenantWebhookHarness`. p99 < 200ms + fairness ≥ 0.85 under 5×200rps×5s; replay-100× with fixed `event_id` proves exactly 1 outbox row; cross-tenant signature returns 401 with zero DB writes in either tenant.
4. **Runtime smoke of Aspire mock-server wiring** — DEFERRED (same as Sprint-4): Docker daemon not running on this dev machine. CI is the canonical validation. Sprint-5 work happens to share the same Aspire stack, so the first Sprint-5 integration run also exercises the mock-server round-trip.

### Brainstorm R6 → Plan U3 correction (documented in plan + here)

The brainstorm proposed "emit OrderImportedV1 with `InternalSku=null` on unmapped lines." That was structurally impossible against canon — the existing `OrderImportedLineV1.Sku` is a non-nullable `string`, AND the contract docs explicitly state: *"Unmappable lines fail the whole import at the receiver per Sprint-4 plan Open Questions (status set to Failed on the webhook_events row, no OrderImportedV1 emitted)."* The plan honored canon, and U3 implements fail-whole-import: `webhook_events.status=Failed`, no outbox row, controller returns HTTP 200 with `{ status: "import_failed", reason: "unmapped_skus", unmapped: [...] }`. The row remains for operator-side replay after a manual `IProductMappingRepository.UpsertManualAsync`.

## Deferrals (carried forward — same shape as Sprint-1/3/4)

- **Runtime smoke** — Docker daemon was not running locally during Sprint-4.5 development. CI runs the full integration + Load suite. Once a Docker-enabled dev session lands, this sign-off table gets the actual p99 + fairness numbers as a one-line postscript.
- **Event-type policies beyond `order.created`** — Sprint-4.5 ships `order.created` → emit `OrderImportedV1`; everything else persists the `webhook_events` row but emits no outbox row (via a sentinel `WebhookEventSkippedV1` event-type the registry treats as `PublishDefault` with no subscriber). Per-event-type downstream policies (e.g., `order.cancelled` → emit `OrderCancelledV1`) land in Sprint-6+ alongside Lazada.
- **Mapping batch resolution** — `IProductMappingService.ResolveAsync` is per-line. If U5's burst measurements surface this as a hotspot at 200rps × 5 tenants, a `ResolveBatchAsync(channelId, externalSkus[])` port lands as fast-follow. The cost is bounded (in-process Levenshtein); first CI nightly run validates.

## What this sign-off does NOT claim

- **No wall-time scale-gate numbers yet** — bodies ship runnable; the dev-laptop measurement waits on Docker. CI's first nightly run posts the actual p99 + fairness numbers.
- **No multi-instance dispatcher leader election** — still a Phase-2 nice-to-have (single-instance dispatcher fine for current load).
- **No webhook receiver auth hardening** (IP allowlist, per-channel header allowlist) — Phase-2 hardening, separate from Sprint-4.5's scope.
- **No CSharpier formatting cleanup of the 23 pre-existing drift files** — separate Phase-2-cleanup commit, still open.
