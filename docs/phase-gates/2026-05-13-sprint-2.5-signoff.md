## What this closes

### Sprint-2-redux U9 (carry-forward issue) — closed

Two integration tests in `tests/ShopFlow.Inbound.IntegrationTests/InboundToInventoryFlowTests.cs` provision **a single physical Testcontainers Postgres database**, apply both Inbound's and Inventory's migrations against that same DB, and drive the full flow:

1. Inbound API → `ConfirmReceivingLineService` → row lands in `inbound_outbox_messages`
2. Test pulls the row out + deserialises the JSON payload back to `InboundConfirmedV1`
3. Publishes through MassTransit's in-memory `TestHarness` (substitutes for the multiplexed dispatcher's poll loop — Sprint-1-redux already validates the dispatcher loop end-to-end for `StockReservedEvent`)
4. `InboundConfirmedConsumer` in the Inventory module consumes the message, INSERTs an `inbound_dedup` row, applies `AdjustAtBinAsync` (auto-creates `stock_items` + UPSERTs `stock_item_bins` + updates `bins.occupancy_qty` + writes audit row, all in one ReadCommitted transaction)
5. Assertions verify `stock_items.available`, `stock_item_bins.quantity`, `bins.occupancy_qty`, `inbound_dedup` row existence, and (for the mismatch test) the `reconciliation_tickets` row landed in Inbound's schema with the correct expected/actual quantities.

The shared-DB shape that broke Sprint-2-redux U9 (`outbox_messages` name collision when both modules' migrations target `public` schema) now works because Sprint-2.5's U1+U2 prefixed the tables per-module.

### Latent JSON-options drift — fixed

While building U3 the consumer rejected every message with `payload TenantId 00000000-0000-... does not match envelope TenantId 374adad7-...`. Root cause: the outbox **writers** (SharedKernel `OutboxInterceptor`, Inbound's `InboundOutbox`, Inventory's `ReservationRepository.AppendOutbox`) each held a private `JsonSerializerOptions` with `PropertyNamingPolicy = CamelCase`. The dispatcher's **reader** (`MultiplexedOutboxDispatcher.DispatchOneTenantAsync`) called `JsonSerializer.Deserialize(payload, type)` with **default options** (case-sensitive PascalCase). The JSON keys were `tenantId` / `purchaseOrderLineId` / etc., but the deserializer looked for `TenantId` / `PurchaseOrderLineId` — none of the contract properties got populated; everything came back as default values.

This bug shipped in Sprint-1-redux. It was latent because Sprint-1-redux never exercised an actual consumer reading payloads — the dispatcher published events into MassTransit's bus, but no consumer (cross-module or otherwise) was reading them. Sprint-2-redux's `InboundConfirmedConsumerTests` (U6) didn't catch it either because they used `harness.Bus.Publish(msg)` with a fully typed object, bypassing the outbox-row JSON round-trip. Sprint-2.5's cross-module flow test is the first time JSON serialise + deserialise happens in the same test.

**Fix**: introduce `ShopFlow.SharedKernel.Infrastructure.OutboxJsonOptions.Default` — a single static `JsonSerializerOptions` instance with `PropertyNamingPolicy = CamelCase` AND `PropertyNameCaseInsensitive = true`. Replaced four private option declarations:
- `OutboxInterceptor.SerializerOptions` (write side, SharedKernel)
- `MultiplexedOutboxDispatcher` deserialize call (read side, SharedKernel)
- `InboundOutbox.JsonOptions` (Inbound)
- `ReservationRepository.OutboxJsonOptions` (Inventory, Sprint-1-redux)

The `PropertyNameCaseInsensitive = true` flag is a safety net so older PascalCase-keyed payloads (none exist in this repo yet but the cost is zero) round-trip cleanly should the policy ever shift.

## Deviations from precedent

- **Phase-0-redux migration edited in-place**: the Inventory `20260512000001_InitialInventorySchema` migration (Phase-0-redux U8 deliverable) is edited in place to rename `outbox_messages` → `inventory_outbox_messages`. No production tenants have been provisioned against the prior name — a separate rename migration would have been unnecessary ceremony. Documented inline in the migration. Carry-forward rule: once a migration applies to a production tenant DB, this in-place edit option is off the table; add a new rename migration.

## What this sign-off does NOT claim

- No real RabbitMQ Testcontainers run. The dispatcher loop still uses the in-memory test harness — Sprint-1-redux's validation of the dispatcher's outbox-read + publish path stands as the broker-layer evidence. First RabbitMQ failure modes (publish error, redelivery, DLQ) surface in nightly CI on Linux.
- No `MultiplexedOutboxDispatcher` end-to-end test for the new Inbound dispatcher instantiation. The dispatcher code is shared with Sprint-1-redux's Inventory instance — same loop, same code paths, same outbox query shape. A focused dispatcher test (if anything in the dispatcher logic ever changes) is a small unit-test follow-up.
