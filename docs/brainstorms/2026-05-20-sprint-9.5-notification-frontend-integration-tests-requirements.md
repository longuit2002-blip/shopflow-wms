# Sprint-9.5 — Notification module + Frontend Auth UX + Cross-tenant Integration Tests

## Summary

Sprint-9.5 closes the six units deferred from Sprint-9 in a single tag `v0.13.0-sprint-9.5`: lands `ShopFlow.Notification` as the 7th business module (outbox + log + dead-letter shape, Mailpit dev SMTP, MailKit prod SMTP, 4 consumers + 4 templates × 2), ships the full frontend auth experience (useAuth perm[] + httpClient 401/403 split + MFA challenge/enrollment branches + 5 new screens at Sprint-6/7 polish + Owner admin surface), and adds AuthCrossTenantTests + 4 KTD-pinning integration tests against Testcontainers Postgres + Redis. Frontend UI affordances start gating on the JWT `perm[]` array ahead of Sprint-10+'s backend `[Authorize(Policy=...)]` migration.

---

## Problem Frame

Sprint-9 shipped the backend auth foundation — RBAC + TOTP MFA + chain-aware refresh + per-account lockout + per-IP rate limit + self-service password reset — but ended with six deferred units that together make the foundation unusable end-to-end. The 4 cross-module Auth events (`PasswordResetRequestedV1`, `RefreshReuseDetectedV1`, `AccountLockedV1`, `MfaEnrolledV1`) currently publish to RabbitMQ + idle in MT durable queues with no consumers, so:

- A user who clicks "Forgot password?" gets a constant-time 200 back, but no email ever arrives.
- A Refresh-reuse event fires from `RefreshTokenCommandHandler.HandleTombstonePathAsync`, the chain is revoked, but the Owner is never told.
- The Sprint-9 endpoints (`/api/auth/forgot-password`, `/api/auth/mfa/enroll/begin`, `/api/auth/mfa/verify`, `/api/auth/recovery-codes`, the 4 admin endpoints) exist + return correct shapes, but no UI calls them. The endpoints are unreachable from the existing LoginScreen + Sidebar.
- The Owner role is force-enrolled for MFA (`mfa_required = true` per Sprint-9 R17 + U12 OwnerSeed change), but the LoginScreen has no MFA challenge branch and no enrollment screen. An Owner cannot complete a successful login today.
- The KTD13 OwnerCritical guard is unit-covered in `RolePermissionsCommandHandlerTests`, but the full PUT `/api/auth/admin/role-permissions` → 422 → DB row check round-trip is not exercised against a real Postgres + JWT-issuing kernel. The KTD1 perm-array shape has unit + JwtTokenIssuer-round-trip coverage, but not a full JwtBearer-validated request hitting a policy-gated endpoint.

Plus the broader Sprint-10+ payoff: without the Notification module landed now, every future cross-cutting transactional email need (order milestone alerts, channel webhook anomalies, MFA enrolled confirmation, future operator pager) would have to invent the consumer + retry + template + dead-letter pattern ad-hoc. Sprint-9.5 is the natural landing slot.

The cost of NOT shipping Sprint-9.5: Sprint-9's backend foundation is portfolio-incomplete — emails never deliver, Owners can never complete the forced-MFA enrollment, the admin surface stays Sprint-8-shaped, and the 4 cross-module contracts ship as no-op publishes that document an unfilled gap rather than a working pipeline.

## Actors

- **A2. Picker / Dispatcher**: may opt into TOTP via profile menu; subject to lockout + rate limit + UI affordance gating via `perm[]` claim; cannot reach admin surface (route guard).
- **A3. Anonymous user (pre-login)**: hits login + forgot-password + reset-password screens; subject to per-IP rate limit + per-account cooldown.
- **A4. Auth.Api**: already ships Sprint-9 endpoints; no new endpoints in Sprint-9.5. Issues access tokens carrying the `perm[]` JSON-array claim (KTD1) that the frontend will read.
- **A5. ShopFlow.Notification (NEW)**: 7th business module — consumes Auth's 4 outbox events via MassTransit; renders Vi/En templates (English-only at Sprint-9.5 ship time pending `users.preferred_locale`); writes to its own outbox → background dispatcher → log/DLQ; sinks via `IMailerProvider` (LoggingMailer dev-default + MailKitSmtpMailer prod).
- **A6. Mailpit container**: dev SMTP target; Aspire AppHost resource (mirrors Sprint-2-redux RabbitMQ pattern); browsable web UI at `mailpit:8025` for inspecting captured emails.
- **A7. Frontend client**: useAuth state machine extended with three auth-states (full-session / mfa-challenge / mfa-enrollment); httpClient interceptor learns the 401/403 split; 5 new screens land at Sprint-6/7 design fidelity; Owner admin surface gains 3 sections.
- **A8. shopflow-migrate CLI**: extended to register `ShopFlow.Notification` migrations via `IModuleMigrationRegistry` (Sprint-9 U12 deferral); applies notification schema during `provision --tenant=<slug>`.

## Key Flows

- F1. **Password reset email delivery (Auth → Notification → SMTP)**
  - **Trigger:** A3 submits `/api/auth/forgot-password` with valid email; Auth.Api emits `PasswordResetRequestedV1` to `auth_outbox_messages`.
  - **Actors:** A3, A4, A5, A6
  - **Steps:** MultiplexedOutboxDispatcher publishes to RabbitMQ. A5's `PasswordResetRequestedConsumer` consumes; renders the password-reset template (English-only; deep link includes plaintext token + workspace subdomain); writes a row to `notification_outbox` with status=pending; acks the MT message. A5's background dispatcher (`MultiplexedOutboxDispatcher<NotificationDbContext>`) polls `notification_outbox`, picks up the row, calls `IMailerProvider.SendAsync` (Mailpit in dev, MailKit SMTP in prod). On success: insert `notification_log` row with status=sent + provider response code; delete the outbox row. On transient failure: retry curve (3 attempts with backoff); after final failure → move to `notification_dead_letter` with last error.
  - **Outcome:** User receives the reset email; A1 (Owner) can inspect dead-letter rows for delivery audit.
  - **Covered by:** R1, R3, R5, R7, R8, R9, R10

- F2. **Owner first-login MFA enrollment**
  - **Trigger:** A1 submits valid password to `/api/auth/login`; backend returns `mfa_enrollment_required` short-lived intent token (Sprint-9 LoginCommandHandler 3-way branch).
  - **Actors:** A1, A4, A7
  - **Steps:** Frontend useAuth transitions to `mfa-enrollment` state and stores the intent token (memory only, never localStorage). httpClient interceptor switches off 401-refresh during this state (no refresh token exists). LoginScreen redirects to `/mfa/enroll`. User clicks "Begin enrollment" → POST `/api/auth/mfa/enroll/begin` with intent token in Authorization header → response carries QR otpauth SVG (`Cache-Control: no-store` per KTD16) + manual secret + enrollment UUID. User scans QR with authenticator app, enters first OTP, clicks "Verify" → POST `/api/auth/mfa/enroll/verify`. On success: response carries `RecoveryCodes` (10 codes, plaintext, displayed ONCE) + the real access+refresh pair. RecoveryCodesDisplay component shows the codes with explicit "Download as .txt" button + mandatory "I have saved my recovery codes" checkbox before Continue. useAuth transitions to `full-session`; Notification consumes `MfaEnrolledV1` from outbox.
  - **Outcome:** Owner has working TOTP + recovery codes saved; cannot navigate past `/mfa/enroll` until enrollment completes.
  - **Covered by:** R11, R12, R13, R14, R15, R16, R17

- F3. **Standard login with existing MFA (Owner second-login onward; opted-in Picker/Dispatcher)**
  - **Trigger:** A1/A2 submits valid password to `/api/auth/login` for a user with `mfa_enrolled = true`.
  - **Actors:** A1 or A2, A4, A7
  - **Steps:** Backend returns `mfa_challenge_required` intent token (5-min HMAC-SHA256 compact token per Sprint-9 KTD with `IMfaChallengeTokenCodec`). useAuth transitions to `mfa-challenge` state. httpClient skips 401-refresh in this state. Frontend redirects to `/mfa/challenge` (auto-focus 6-digit input + paste-friendly). User enters OTP → POST `/api/auth/mfa/verify` with challenge token + OTP → on success returns real access+refresh pair + useAuth transitions to `full-session`. On 3 consecutive bad OTPs: useAuth clears mfa-challenge state + redirects to /login with toast "Your session expired. Please log in again." (the underlying Sprint-9 lockout already increments `failed_login_count`).
  - **Outcome:** Token pair issued only after both factors verify; lockout enforced.
  - **Covered by:** R11, R12, R17, R20

- F4. **httpClient 401/403 split during normal session**
  - **Trigger:** Any frontend mutation or query hits a Sprint-9 endpoint and receives 401 (expired access token) or 403 (permission denied).
  - **Actors:** A1/A2, A7
  - **Steps:** On 401, httpClient consults useAuth state: if `full-session`, attempt single-flight refresh (Sprint-8 inflight-refresh-guard preserved); on refresh success retry the original request with new access token; on refresh failure (post-grace replay → `ChainRevoked`) clear session + redirect /login + toast "Your session was signed out (possible credential reuse detected). Please log in again." On 403, httpClient does NOT attempt refresh — surface as toast "You do not have permission to perform this action" + the original error code from problem-details JSON; do NOT clear session.
  - **Outcome:** 401 triggers session preservation via refresh OR clean sign-out; 403 surfaces to user without session disruption.
  - **Covered by:** R18, R19, R21

- F5. **Owner edits role permissions for Picker**
  - **Trigger:** A1 navigates to /admin/role-permissions (route guarded by `perm[]` contains `auth.admin.role-permissions.update`).
  - **Actors:** A1, A4, A7
  - **Steps:** RolePermissionsEditor renders 3 columns (Owner read-only with all 24 keys checked + visual lock icon, Picker editable, Dispatcher editable) grouped by module (Auth admin / Inventory / Outbound / Inbound / Hub). User toggles 2 Picker permissions, clicks Save. Frontend computes diff and confirms via modal showing added/removed keys. On Continue: PUT `/api/auth/admin/role-permissions` with `{ role: "Picker", permissionKeys: [...] }`. On 422 `auth.role_permissions_owner_critical_locked` (only possible if user manipulates request body to target Owner): inline error + abort. On 200: toast "Picker permissions updated. Changes propagate within 15 minutes." (token-TTL hint per Sprint-9 R5). RolePermissionsChangedV1 written to outbox for future audit-stream consumers (Sprint-10+ Analytics).
  - **Outcome:** Picker `role_permissions` rows updated; affected Picker sessions reload new `perm[]` on next refresh-token rotation (≤15 min).
  - **Covered by:** R28, R29, R30, R31

- F6. **Refresh-reuse → Owner alert email**
  - **Trigger:** A presented refresh token's tombstone exists AND grace window expired (Sprint-9 KTD3 / chain-aware revoke).
  - **Actors:** A4, A5, A6, A1 (recipient)
  - **Steps:** RefreshTokenCommandHandler emits `RefreshReuseDetectedV1` to `auth_outbox_messages` carrying chain_id + user_id + presenting_ip + user_agent + UTC timestamp. A5's `RefreshReuseDetectedConsumer` consumes; renders Owner alert template with the affected user's email + presenting IP + timestamp; writes to `notification_outbox`; dispatcher delivers via the F1 path. Owner receives an email "Suspicious activity on account {email}: a previously-rotated session token was replayed from IP {ip} at {time} UTC. That session has been signed out. If this wasn't you, change your password immediately."
  - **Outcome:** Owner has visibility on chain-reuse incidents within seconds.
  - **Covered by:** R1, R4, R7, R8, R9

## Requirements

**Notification module shape (U10)**

- R1. New `ShopFlow.Notification` 7th business module follows the canonical quartet (Domain + Application + Infrastructure + Api). Domain holds the minimum value objects to express `NotificationKind` + `Recipient` + `RenderedEmail` (subject + body-text + body-html); Application owns the consumer interfaces + `IMailerProvider` port; Infrastructure owns the DbContext + EF migrations + 4 MT consumers + `MailKitSmtpMailer` + `LoggingMailer` + `SimpleTemplateRenderer`; Api hosts the dispatcher background service + minimal health endpoint. The Api is a hosted service host (no public REST surface beyond `/health`).
- R2. `Notification.Infrastructure` registers via `services.AddNotificationModule(IConfiguration)`; the registration wires the 4 MT consumers, the dispatcher background service, the mailer provider chosen via `Notification:Mailer:Provider` ∈ {Logging, MailKitSmtp}, and the per-module outbox interceptor.
- R3. Per-module schema persists 3 tables: `notification_outbox` (status=pending after MT consume, payload=fully-rendered email), `notification_log` (terminal success; UNIQUE on `(source_event_id, recipient)` for cross-instance dedup), `notification_dead_letter` (terminal failure with `attempt_count` + `last_error_code` + `last_error_message`). All tables carry `id`, `created_at`, `updated_at` per kernel convention. Migration registered via `IModuleMigrationRegistry` so `shopflow-migrate provision --tenant=<slug>` applies it (closes Sprint-9 U12 deferral).

**Email delivery semantics (U10 + U11)**

- R4. MT consumers (one per event type: `PasswordResetRequestedConsumer`, `RefreshReuseDetectedConsumer`, `AccountLockedConsumer`, `MfaEnrolledConsumer`) render the template + write the rendered email to `notification_outbox` + ack the MT message. Consumers do NOT call the mailer directly — that decouples MT throughput from SMTP latency.
- R5. Background dispatcher (`MultiplexedOutboxDispatcher<NotificationDbContext>`) polls `notification_outbox` per tenant, claims rows via `FOR UPDATE SKIP LOCKED`, calls `IMailerProvider.SendAsync`, and on terminal success deletes the outbox row + inserts `notification_log`; on transient failure increments `attempt_count`; on terminal failure (attempt_count exceeds `Notification:Dispatcher:MaxAttempts`) inserts into `notification_dead_letter`.
- R6. `IMailerProvider` exposes `Task<MailerResult> SendAsync(RenderedEmail email, CancellationToken ct)`; `MailerResult` is `Result<MessageId>` with stable error codes `mailer.transient.*` (retryable) vs `mailer.permanent.*` (terminal). MailKitSmtpMailer maps SMTP response codes (4xx → transient, 5xx → permanent); LoggingMailer is the dev-default (writes a structured log line + always returns success; used when Mailpit unavailable). The provider switch is `Notification:Mailer:Provider` config; the default in `appsettings.Development.json` points at `MailKitSmtp` against `Notification:Mailer:Mailpit:Host` (Aspire DNS resolves to the Mailpit container).
- R7. Idempotent consumption is guarded by UNIQUE on `notification_log(source_event_id, recipient)` — a duplicate MT redelivery races into the outbox but the dispatcher's INSERT into `notification_log` fails on the second attempt + the second outbox row is silently dropped (logged at debug). No double-send.
- R8. `SimpleTemplateRenderer` substitutes `{placeholder}` tokens against a flat dictionary. No conditionals, no loops — the 4 templates are simple enough. Templates ship as 8 embedded resources (4 events × 2 mime types: `.txt` + `.html`) under `Notification.Infrastructure/Templates/`. Templates are English-only at Sprint-9.5 ship time; bilingual templates wait for `users.preferred_locale` (Sprint-10+).
- R9. Mailpit container added to Aspire AppHost as a resource using `bitnami/mailpit` or equivalent published image. Aspire wires hostname + 1025 SMTP + 8025 web UI exposed to `localhost` for browsing. Notification.Api references the resource via `WithReference(mailpit)`. CI smoke runs Mailpit via Testcontainers fixture in `NotificationIntegrationTests`.
- R10. Dead-letter rows are an operator surface: not exposed via REST in Sprint-9.5; Owners inspect via direct DB query during incident response. Sprint-10+ adds a `/admin/notification-dlq` UI tab.

**Frontend useAuth + httpClient (U13)**

- R11. `useAuth` Zustand store extended with `authState: 'full-session' | 'mfa-challenge' | 'mfa-enrollment' | null` discriminator + `intentToken: string | null` (only populated during mfa-challenge / mfa-enrollment). `perm: readonly string[]` field exposed on the `user` object (extracted from JWT `perm[]` claim during login response + refresh-rotation response). `intentToken` lives in-memory only (Zustand state); never persisted to `localStorage` because intent tokens are 5-min-lived and reload-on-recover is by design (user re-logs in).
- R12. `useAuth.login(request)` shape returns a discriminated union: `{ kind: 'success', user, accessToken, refreshToken }` | `{ kind: 'mfa-challenge', intentToken, mfaMethods }` | `{ kind: 'mfa-enrollment', intentToken }` | `{ kind: 'failure', errorCode }`. The shape mirrors Sprint-9 LoginResponse all-nullable + MFA-flags contract.
- R13. `httpClient` interceptor reads `useAuth.authState` before deciding 401 behavior. In `full-session`, 401 triggers the existing single-flight refresh + retry pattern (Sprint-8 inflight-refresh-guard + idempotency-key-persisted-across-retry preserved). In `mfa-challenge` / `mfa-enrollment`, 401 clears the intent token + redirects to `/login` (no refresh attempted). When the store has no session, 401 redirects to `/login` immediately.
- R14. `httpClient` 403 handling: surface to caller via the existing `HttpError` shape (status + errorCode from problem-details JSON), never trigger refresh, never clear session. The caller (useQuery / useMutation hook) translates the toast.
- R15. `usePerm(...keys: string[]): boolean` hook returns true iff every requested permission key is in `useAuth.user.perm`. Used at affordance-render time (button visibility) + sidebar item visibility + admin route guards. Returns false when `useAuth.user` is null. Pure function over the store; memoized.

Always shows "If your email is on file, you'll receive a reset link within 5 minutes" success state regardless of backend result (R6 enumeration discipline). Tied to /login via "Forgot password?" link below the password field.
- R17. `/reset-password` route: parses `?token=<base64url>` from URL; if absent or malformed, render error panel "This link is invalid or has been used. Request a new reset link." with Continue button → /forgot-password. Form: new password + confirm-password + submit. Validation matches Sprint-8 password complexity rules (min 12 chars, 4-category mix). On 200: redirect /login with toast "Password reset. Please log in with your new password." On 422 `auth.reset_token_invalid|expired|used`: inline error.
- R18. `/mfa/enroll` route: gated by useAuth.authState === 'mfa-enrollment'. Sections: Step 1 "Scan this QR code with your authenticator app" (QR otpauth SVG fetched via `GET /api/auth/mfa/enroll/begin`; manual secret displayed as monospace fallback) → Step 2 "Enter the 6-digit code from your authenticator" (form) → Step 3 (post-verify) "Save your recovery codes" (RecoveryCodesDisplay with mandatory acknowledgement checkbox + Download as .txt button + "Continue" disabled until checked). - R21. All 5 screens match Sprint-6/7 design system: tokens.css palette + spacing + Drawer/Modal/Toast primitives + role=switch toggles + Vi/En labels via existing `labelsFor` (English-only EMAIL templates; UI screens remain bilingual to maintain Sprint-6/7 parity) + Drawer/Modal Esc-capture coexistence (Sprint-6 KTD9). a11y smoke harness extends with 5 new cases (one per screen) + 1 for RecoveryCodesDisplay.

## Acceptance Examples

- AE1. **Covers R4, R5, R7.** Given a tenant where `PasswordResetRequestedConsumer` has just consumed an event for `alice@example.com`, when MassTransit redelivers the same envelope due to a broker hiccup, then the second consume writes a fresh `notification_outbox` row but the dispatcher's `notification_log` INSERT fails on UNIQUE; the duplicate outbox row is dropped + logged at debug; Alice receives exactly one email.
- AE2. **Covers R5, R6.** Given a `notification_outbox` row whose `IMailerProvider.SendAsync` returns `Result.Failure("mailer.transient.smtp_4xx")`, when the dispatcher next polls, then `attempt_count` increments by 1; the row stays in `notification_outbox`. When `attempt_count` reaches `MaxAttempts`, then the dispatcher inserts a `notification_dead_letter` row + deletes the outbox row + emits a structured log entry at Error level.
- AE3. **Covers R11, R12, R13.** Given a user with `mfa_enrolled = true`, when the user submits valid password to /login, then useAuth.authState becomes `mfa-challenge` + the intent token is stored in memory; the next `httpClient` request returning 401 does NOT attempt refresh; the user is redirected to `/login` with the "session expired" toast.
- AE4. **Covers R15, R28, R29, R30.** Given a Picker user whose `perm[]` is empty, when the user logs in successfully, then the sidebar shows only Dashboard + Profile (Inventory / Orders / Inbound / Admin all hidden); direct URL `/admin/users` redirects to `/dashboard` with the permission toast; any in-page action button is hidden via `usePerm`.

## Key Decisions

- **All 6 deferred units in one tag** — single `v0.13.0-sprint-9.5` instead of split into Sprint-9.5a/b. Rationale: each unit's value depends on the others (Notification without frontend ⇒ no user-facing trigger paths; frontend without Notification ⇒ "click to send reset email" with no email arriving). The bundle is the demo-able milestone.
- **Outbox + log + DLQ in Notification, not just synchronous send** — mirrors Auth/Inbound/Outbound multiplexed dispatcher pattern. Decouples MT consumer throughput from SMTP latency; matches every other module's persistence shape; the DLQ is a real operator surface during outages. Cost: +1 background dispatcher hosted service in Notification.Api; +2 tables vs the minimum.
- **Permission-based UI gating ships ahead of backend `[Authorize(Policy=...)]` migration** — frontend reads `perm[]` Sprint-9 already emits; sets the Sprint-10+ pattern. Trade-off: there's a brief window where a manipulated UI could bypass affordance hiding, but the backend still enforces `[Authorize]` + role checks where they exist today; the gap is no worse than Sprint-8's role-only gating.
- **English-only email templates at v0.13.0** — bilingual (Vi/En) templates wait for `users.preferred_locale` (Sprint-10+). UI screens stay bilingual per Sprint-6/7 parity. Pragmatic split: UI locale is per-session-controllable; email locale is per-recipient and needs per-user persistence.
- **Mailpit as dev SMTP, MailKit as prod** — Mailpit replaces "raw mock SMTP" with a browsable web UI for development; MailKit (existing .NET SMTP library) handles real SMTP via Sendgrid / SES / etc. credentials at deploy time. The `IMailerProvider` switch is config-driven.
- **The 4 KTDs pinned by integration tests are KTD1 / KTD2 / KTD10 / KTD13** — selected for layer-spanning coverage (JWT roundtrip, Redis multi-record, AES cipher + key-id slot, full PUT round-trip). The remaining 12 Sprint-9 KTDs are unit-covered.
- **MFA enrollment intent token is in-memory only** — never persisted to localStorage. Reload during enrollment forces a fresh login (5-min token TTL makes this acceptable). Avoids a vulnerability surface where a half-completed enrollment leaks an enrollment intent.
- **Notification.Api is a hosted-service host, not a public REST surface** — `/health` is the only endpoint. Sprint-10+ may add `/admin/notification-dlq`.
