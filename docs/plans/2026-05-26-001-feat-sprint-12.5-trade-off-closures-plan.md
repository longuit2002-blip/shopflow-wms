# feat: Sprint-12.5 trade-off closures

## Summary

Six-unit ~1-week patch release that closes the five Sprint-12 trade-offs: wires `IAuthAuditLogRepository.AppendAsync` into the 12 Auth command handlers that map to one of the 15 documented `EventType` keys, adds `actor_user_id` to `outbound_saga_transitions` with actor propagation via saga event payloads, ships `MarkShipFailed` reusing Sprint-3-redux Path B compensation primitives as Path C, adds a deterministic tier-3 carrier-retry integration test, and documents the MFA + first-login production-hardening deferrals in Auth AGENTS.md. Tag `v0.16.1-sprint-12.5` matches the Sprint-X.5 cadence (2.5 / 4.5 / 7.5 / 8.5 / 10.5).

---

## Problem Frame

Sprint-12 shipped the Dispatcher role + 3-role hand-off proof but explicitly carried forward five trade-offs in [`docs/phase-gates/2026-05-22-sprint-12-signoff.md`](../phase-gates/2026-05-22-sprint-12-signoff.md). Each gap has a visible cost — the audit log table is storage-but-unused since Sprint-9, the saga transitions table has no operator attribution, the saga has no ship-failure compensation path, the Polly retry pipeline has unit-but-not-HTTP coverage, and the production-hardening deferrals (MFA + first-login) are not yet codified. See [`docs/brainstorms/2026-05-26-sprint-12.5-trade-off-closures-requirements.md`](../brainstorms/2026-05-26-sprint-12.5-trade-off-closures-requirements.md) for the full pain narrative.

## Requirements

**Auth audit log wiring**
- R1. Each of the 12 Auth Application command handlers that map to one or more of the 15 documented `EventType` keys must call `IAuthAuditLogRepository.AppendAsync` at every terminal emit (one row per `EventType` per outcome).
- R2. Audit writes are fire-and-forget at the handler call site — a write failure logs at Warning and does NOT propagate to the HTTP response.
- R3. `metadataJson` captures event-type-relevant context (e.g., `auth.login.failed` → `{ "reason": "auth.invalid_credentials" }`; `auth.role_permissions.changed` → `{ "added": [...], "removed": [...] }`).
- R4. `auth_audit_log` schema is unchanged for this unit.

**Outbound saga actor attribution**
- R5. `outbound_saga_transitions` carries a new nullable `actor_user_id` (uuid) column. Operator-initiated transitions (ConfirmPick / MarkPickFailed / ConfirmPack / ConfirmShip / MarkShipFailed) populate it; system-triggered transitions leave NULL.
- R6. Actor flows from `IRequestContext.UserId` (canonical) on the controller through the saga event payload (additive `Guid? ActorUserId` field on `PickConfirmed`/`PickFailed`/`PackConfirmed`/`ShipConfirmed`/new `ShipFailed`) into `SagaTransitionObserver.RecordTransitionAsync`.
- R7. Additive migration ships with the unit; historical rows backfill to NULL.

**`MarkShipFailed` feature**
- R8. New endpoint `POST /api/v1/outbound/orders/{id}/mark-ship-failed` gated by `[Authorize(Policy = PermissionKeys.OutboundOrdersShipConfirm)]` — same policy as ConfirmShip; no new permission key; Dispatcher + Owner baselines unchanged.
- R9. If `Order.Status != AwaitingShip`, returns 422 with errorCode `order.invalid_state`; no saga event published; no audit row. The `[Authorize(Policy)]` filter still fires before this check (Sprint-12 adversarial-F3 invariant).
- R10. Handler publishes new `ShipFailed` saga event. Saga transitions `Packed → CompensatingReservation`, publishes `ReleaseStockV1`, drains `StockReleased` counter, terminal `Cancelled`.
- R11. Saga's `CompensatingReservation` IfElse activity requires no modification — the existing `WhenEnter(CompensatingReservation, x => x.IfElse(...))` gate checks `ReservedLineSkus` count and is entry-path-agnostic. Path C (Packed + ShipFailed) reuses Path B (AwaitingPick + PickFailed) compensation primitives unchanged: `LinesAwaitingRelease` + `ReservedLineSkus` set on `AwaitingReservation → Reserved` survive through `AwaitingPick → Picked → AwaitingPack → AwaitingShip`.
- R12. Idempotent via natural-409 pre-state check (KTD6). Source inspection confirmed `MarkPickFailedAsync` has no `Idempotency-Key` header processing — the brainstorm R12's claim that header-keyed dedup is "MarkPickFailed precedent" was factually wrong. Natural-409 mirrors the actual existing precedent; header-keyed dedup defers to a Sprint-13+ workstream when an Outbound use case demands it.
- R17. `MarkShipFailedRequest.Reason` AND `MarkPickFailedRequest.Reason` both carry a 1000-character maximum length. The new endpoint enforces server-side via `[MaxLength(1000)]` on the record property + explicit length check; the existing MarkPickFailed endpoint gets the same retrofit (KTD10). Closes the inherited DoS / outbox-bloat vector surfaced by Sprint-12.5 doc-review.

**Tier-3 carrier-retry E2E**
- R13. New `[Fact(Skip = ...)]` test exercises the Polly retry path through HTTP: HandoffFixture configured with non-zero flake rate + shortened delays, ConfirmShip invoked, retry observed, success returned. Skip-marked locally; CI runs unskipped.
- R14. Total wall-time under 5 seconds; per-attempt delay ≤50ms via `MockShippingProvider` min/max-delay knobs.

**Documentation deferrals**
- R15. Auth AGENTS.md gains a `Production-hardening obligations` subsection naming Picker/Dispatcher MFA enforcement and force-change-on-first-login as deferred work, with the code change each requires when implemented.
- R16. Sign-off commit ships: `docs/phase-gates/2026-05-26-sprint-12.5-signoff.md`, CLAUDE.md current-stage paragraph, CHANGELOG entry, annotated tag `v0.16.1-sprint-12.5`.

## Key Technical Decisions

- **KTD1 — Audit fire-and-forget at handler call site, NOT in repository.** `IAuthAuditLogRepository.AppendAsync` awaits `SaveChangesAsync` (research confirmed). Each handler wraps the call in try/catch + Warning log. Rationale: repository contract stays simple; failure-handling policy lives at the consumer.
- **KTD2 — Audit-log scope is 12 handlers / 15 documented EventType keys, NOT all 16 command handlers.** Handler-count reconciliation: brainstorm R1 stated "14 Auth Application command handlers" — that count was approximate. Repo research confirms 16 distinct `*CommandHandler.cs` files in `src/Services/Auth/ShopFlow.Auth.Application/Commands/`. Of those 16, four (`BeginEnrollMfaCommand`, `GenerateRecoveryCodesCommand`, `CreateUserCommand`, `UpdateUserCommand`) have no documented EventType key in the 15-key `IAuthAuditLogRepository` catalog. Sprint-12.5 wires 12 handlers covering all 15 documented keys; Sprint-13+ may expand the catalog to cover the remaining 4. Closes the Sprint-9 storage-but-unused gap correctly without inventing new keys.
- **KTD3 — Actor propagation via saga event payload, NOT saga-state stash.** Each operator-initiated event record gains additive `Guid? ActorUserId`. `RecordTransitionAsync` reads `ctx.Message.ActorUserId`. Alternative (transient field on `FulfillmentSagaState`) would pollute state with a non-essential field; payload propagation is cleaner.
- **KTD4 — `IRequestContext.UserId` is the canonical JWT subject accessor on Outbound controller paths.** Middleware populates it from the JWT claim. Defensive fallback to `User.FindFirst(ClaimTypes.NameIdentifier)` only if null (should not happen post-`[Authorize(Policy)]` filter). Captured as new `docs/solutions/` entry during U2.
- **KTD5 — Path C reuses Path B compensation primitives unchanged.** Existing `WhenEnter(CompensatingReservation, x => x.IfElse(...))` handles Packed-entry transparently — `ReservedLineSkus` + `LinesAwaitingRelease` set on `AwaitingReservation → Reserved` survive through to Packed. No third IfElse branch; no new saga-state column.
- **KTD6 — `MarkShipFailed` idempotency = natural-409 pre-state check, NOT header-keyed dedup.** Brainstorm R12 cited "header-keyed dedup as MarkPickFailed precedent"; source inspection of `MarkPickFailedAsync` (`OrdersController.cs:720-785`) confirms there is no `Idempotency-Key` header processing — the brainstorm R12 reference to MarkPickFailed precedent was factually wrong. Sprint-11 KTD3 `createIdempotentMutation` is a frontend-side ULID factor; backend natural-409 is the established Outbound contract. The plan corrects the brainstorm and adopts the actual precedent.
- **KTD7 — Tier-3 E2E determinism via injectable `Func<double>` random source.** Additive 5-arg constructor on `MockShippingProvider`; existing 3-arg + 4-arg ctors backward-compat. Tests inject a deterministic 2-value sequence so AE6's "fail first, succeed second" assertion is exact. Alternative (probabilistic ≥1-retry assertion) would weaken test signal.
- **KTD8 — Patch version bump `v0.16.1-sprint-12.5`.** Matches Sprint-2.5/4.5/7.5/8.5/10.5 precedent for cleanup-shaped point releases. No net-new role surface or feature surface; minor bump would imply that.
- **KTD9 — `auth.login.failed` audit row stores `submittedEmail` as deliberate forensic trade-off.** Provides credential-stuffing analysis surface (correlate attacker hitting many unknown emails); HTTP response stays uniform `auth.invalid_credentials` per Sprint-9 R6 so enumeration is unaffected at the HTTP layer. Secondary-oracle risk (an attacker with DB read access could query the audit log) is accepted because DB compromise is already severe. PDPA right-to-erasure for cross-tenant email typos is bounded by ADR-0003's per-tenant DROP DATABASE.
- **KTD10 — `Reason` field on `MarkShipFailedRequest` AND `MarkPickFailedRequest` carries a 1000-character max-length guard.** Closes the inherited DoS / outbox-bloat vector (a malicious Dispatcher / Picker could submit ~10MB reasons under the existing precedent). Server-side guard (`[MaxLength(1000)]` on the record property + explicit length check in the controller before persisting) is the canonical defense. Updates MarkPickFailed in-place; technically a Sprint-11 retrofit but the diff is 1-2 lines and the test surface is already in scope.

**Approach:**
- Per handler: inject `IAuthAuditLogRepository _auditLog` + `ILogger<...> _logger`. At each terminal emit branch, wrap `await _auditLog.AppendAsync(...)` in try/catch + `_logger.LogWarning(ex, "Audit write failed for {EventType}", eventType)`. Do NOT propagate.
- **Important framing:** this pattern is **best-effort with exception suppression** — it isolates audit FAILURES from the auth response but NOT audit LATENCY. The handler still awaits the audit insert; a slow Postgres on the tenant DB will increase auth response p99 (`AuthAuditLogRepository.AppendAsync` does `await AddAsync + await SaveChangesAsync`). Sprint-13+ may evolve to a background-channel dispatch if production traces show audit latency contaminating login p99; Sprint-12.5 accepts the coupling because (a) audit writes are small + fast, (b) tenant DBs use PgBouncer transaction pooling, (c) the audit table has no contention beyond inserts.
- **Source IP correctness depends on `ForwardedHeaders` middleware:** `HttpContext.Connection.RemoteIpAddress` is rewritten to the real client IP by Sprint-9 KTD7's `ForwardedHeaders` middleware (wired via `AddShopFlowDefaults` + non-Development boot-time guard requiring `KnownProxies + KnownNetworks`). Auth.Api's `UseShopFlowSecurityPipeline()` includes the middleware. If a future deployment misconfigures `KnownProxies`, the boot guard throws on non-Development (correct fail-closed). Document this dependency in the new fire-and-forget audit pattern docs/solutions note.
- Some handlers emit multiple `EventType` keys from one command. Each terminal branch writes one audit row.
- **`auth.login.locked` semantics (resolved at plan time):** fires once at the lockout boundary attempt — the same `LoginCommandHandler` call that emits `AccountLockedV1`. Subsequent requests against an already-locked account short-circuit at the lockout check before the credential path runs; no additional audit row is emitted for those retries. Matches `AccountLockedV1` cross-module event semantics.
- `metadataJson` shape per key (structured JSON):
  - `auth.login.success` → `{ "tenantSlug": "...", "rememberMe": bool }`
  - `auth.login.failed` → `{ "reason": "auth.invalid_credentials", "submittedEmail": "<not-leaked-to-client-but-stored>" }`
  - `auth.login.locked` → `{ "lockedUntil": "iso-8601" }`
  - `auth.refresh.success` → `{ "chainId": "uuid" }`
  - `auth.refresh.reused` → `{ "chainId": "uuid", "revokedAt": "iso-8601" }`
  - `auth.password.changed` → `{}` (audit row identifies user + action; no extra context needed)
  - `auth.role_permissions.changed` → `{ "targetRole": "...", "added": [...], "removed": [...] }`
  - Others follow similar minimal-but-actionable pattern; finalize per-key during U1.

**Execution note:** Test-first per handler — write the audit-call assertion first, then the handler edit, then verify.

**Patterns to follow:**
- `ForgotPasswordCommand.cs:12-17` — canonical command-record shape with all 3 fields.
- `AuthController.cs:217-218` — canonical request-context extraction (`HttpContext.Connection.RemoteIpAddress?.ToString() ?? "unknown"` + `Request.Headers.UserAgent.ToString()` + `Guid.NewGuid()`).

**Test scenarios:**
- Happy path: `LoginCommand` with valid credentials → 1 `auth.login.success` row with `userId = resolved user-id`, `sourceIp` + `userAgent` from request, non-empty `metadataJson`.
- Happy path: `LoginCommand` with wrong password → 1 `auth.login.failed` row with `userId = null` (R6 enumeration discipline — don't leak user existence via audit either; metadata captures submitted email for forensics).
