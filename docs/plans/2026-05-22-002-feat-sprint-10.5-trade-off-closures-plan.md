# Sprint-10.5 — Trade-off closures (post Sprint-10)

## Summary

Close the five trade-offs Sprint-10 deferred as a ~1-week point release. Fix the frontend `web/src/api/admin.ts` catalog drift (rewrite `PERMISSION_KEYS` to match the 24 backend `PermissionKeys.All` entries exactly — string renames + module collapses + net add/remove leave the cardinality at 24 in both pre- and post-fix states; the drift is shape-only, not count-only; rewrite `OWNER_CRITICAL_KEYS` from 9 entries with one wrong key to 9 matching backend `PermissionKeys.OwnerCritical`). Pin set equality via a backend integration test that parses `admin.ts` at test-time. Attach `[Authorize(Policy = PermissionKeys.HubConnect)]` to `TenantHub`. Add 33 403 wire-shape Docker integration tests across the four controller groups Sprint-10 migrated. Extend Sprint-9.5's `usePerm` / `hasPerm` to every interactive control on Inventory + Orders business pages (Inbound deferred — `/inbound` is the Sprint-6 ComingSoon placeholder). Same point-release cadence as Sprint-2.5 / 4.5 / 7.5 / 8.5.

## Problem Frame

Carried from the [origin brainstorm](../brainstorms/2026-05-22-sprint-10.5-trade-off-closures-requirements.md). In short: Sprint-10 shipped backend per-action policies but the frontend `usePerm()` gate Sprint-9.5 introduced is wired only at route level (Sidebar + `requirePermission()` + RolePermissionsEditor) — buttons / toggles / inline edits on business pages all render unconditionally. The first time a non-Owner role lands (Sprint-11), the UI will show actions the user cannot perform and 403 them. `hub.connect` is catalogued but unattached to `TenantHub`. The Sprint-10 reflection tests pin attribute presence; runtime 403 enforcement is untested against real JWTs with narrowed `perm[]` sets. The frontend `admin.ts` `PERMISSION_KEYS` catalog drifted ~9 of 12 entries from backend `PermissionKeys.All` — invisible today (Owner has all keys via `RolePermissionsSeed`) but becomes a privilege-escalation vector when the first non-Owner role lands.

### U2. Catalog contract pin test — backend integration test parses `admin.ts`

**Goal:** Land a backend integration test in `tests/ShopFlow.SharedKernel.IntegrationTests/` that reads `web/src/api/admin.ts` as a text file, parses out `PERMISSION_KEYS` string literals + `OWNER_CRITICAL_KEYS` string literals, and asserts set equality against backend `PermissionKeys.All` + `PermissionKeys.OwnerCritical` respectively. Drift in either direction fails CI with a clear message naming the offending key(s). Pin the U1 catalog fix and lock it against future regression.

**Requirements:** R13, R14. Covers AE5.

**Dependencies:** U1 (admin.ts must be set-equal to backend before this test can pass).

**Files:**

- `tests/ShopFlow.SharedKernel.IntegrationTests/Authorization/AdminTsCatalogContractTests.cs` (new)
- `tests/ShopFlow.SharedKernel.IntegrationTests/ShopFlow.SharedKernel.IntegrationTests.csproj` (modify if needed — verify the project can resolve the frontend file via relative path; no `<ProjectReference>` needed, just file-system read)

**Approach:**

- Test class sealed, `[Trait("Category", "Integration")]`. Carries three `[Fact]`s: (1) `PermissionKeys.All` set equality, (2) `OwnerCritical` set equality, (3) **module-field validation** (adv-7) — every `PERMISSION_KEYS` entry's `module` field equals one of the values in `MODULES`, AND every `MODULES` entry has at least one key referencing it. Three facts total (per-module pattern doesn't apply; this is a cross-cutting contract).
- Parser logic: locate the frontend file by walking up from the test binary's `AppContext.BaseDirectory` to the repo root (look for `.git` or `ShopFlow.sln`), then resolve `web/src/api/admin.ts`. Read the file text. Anchor the regex specifically on `= [` (the post-equals array literal start) — not on the first `[` after the declaration name, because the type annotation `readonly { ... }[]` contains a bare `[]` that would mismatch a naive anchor (adv-2 / Feasibility F6). Pull every `key: '...'` or `key: "..."` literal between the matching brackets.
- **Count-assertion guard (adv-2 / Feasibility F6)** — BEFORE the set-equality assertion, assert `extracted.Count == 24` for `PERMISSION_KEYS` and `extracted.Count == 9` for `OwnerCritical`. This catches partial-set parser degradation (template literals, multi-line declarations, missed entries due to format changes) that the set-equality alone would not — a degraded parser might extract a subset that happens to be set-equal to the backend, or fail the equality test for the wrong reason. The count guard fails fast with a clear "extracted N keys, expected 24" message before the set-equality runs.
- Assertion: HashSet equality (ordinal) between extracted set and backend `PermissionKeys.All` / `PermissionKeys.OwnerCritical`. On mismatch, the FluentAssertions failure message names the missing-from-frontend + extra-in-frontend sets explicitly (e.g., "Missing from admin.ts: [inventory.skus.write]; Extra in admin.ts: [inventory.skus.create, inventory.skus.update]"). This is the actionable drift-fix message R13 calls for.
- Skip-marked locally only if the frontend file can't be found (e.g., repo root walk fails); CI always finds the file. The test is filesystem-only — no Docker daemon needed — but ships under `Category=Integration` since it crosses the .NET/TS boundary.
- **Sprint-10.6 follow-up note**: if the regex parser proves fragile during U2 implementation or in follow-on sprints, switch to a `ts-node`-emitted JSON sidecar (`web/src/api/admin.permissions.generated.json` checked in alongside `admin.ts`, regenerated by a small `npm run gen:permissions` script). The backend test reads structured JSON instead of regex-parsing TS. Out of Sprint-10.5 scope; the count-assertion + bracket-anchor regex is the in-scope mitigation.

**Patterns to follow:**

- xUnit `[Fact]` + FluentAssertions `.Should().BeEquivalentTo()` for HashSet equality.
- `tests/ShopFlow.SharedKernel.IntegrationTests/` existing project shape (Sprint-2.5 layout per AGENTS.md §11.81).
- `Sprint-10 U1-U4` reflection test pattern for the assertion-message-on-mismatch shape — name the offending entries explicitly.

**Test scenarios:**

- **Covers AE5.** Happy path: at U2 completion, `admin.ts` `PERMISSION_KEYS` set equals backend `PermissionKeys.All` (24 keys each).
- **Covers AE5.** Happy path: `admin.ts` `OWNER_CRITICAL_KEYS` set equals backend `PermissionKeys.OwnerCritical` (9 keys each).
- Count guard (adv-2): `PERMISSION_KEYS` extraction count is exactly 24; `OWNER_CRITICAL_KEYS` extraction count is exactly 9. Catches partial-set parser degradation before the set-equality assertion runs.
- Module-field validation (adv-7): every `PERMISSION_KEYS` entry's `module` value is in the `MODULES` array; every `MODULES` entry has at least one PERMISSION_KEYS reference. Catches misspelled-module bugs where a key silently drops out of the editor's grouped rendering.
- Failure-shape verification: a manual local test (NOT a test method — implementer pokes a key into the wrong shape, runs the test, confirms the failure message clearly names the offending key). Documented as a one-line implementer-time step in U2's verification.
- Edge case: parser handles trailing commas in TypeScript object literal arrays gracefully (TypeScript permits them; the regex must tolerate or skip them).
- Edge case: parser handles single-quoted AND double-quoted string literals (both are valid TS).

**Verification:**

## Key Technical Decisions

- **KTD1 — Backend integration test parses `web/src/api/admin.ts` at test-time.** Implementation: `tests/ShopFlow.SharedKernel.IntegrationTests/Authorization/AdminTsCatalogContractTests.cs` reads the frontend file as text (walks up from `AppContext.BaseDirectory` to repo root), regex-extracts `PERMISSION_KEYS` + `OWNER_CRITICAL_KEYS` string literals, asserts HashSet equality against backend `PermissionKeys.All` + `PermissionKeys.OwnerCritical`. Rationale: (a) backend can do filesystem reads; (b) no new build-step or codegen tooling required; (c) failure message names offending keys explicitly; (d) `[Trait("Category", "Integration")]` runs in CI without Docker requirement (filesystem-only). Resolves origin Deferred Q3.

- **KTD2 — Catalog set equality is bidirectional + frontend admin.ts holds all 24 backend keys including orphans.** `outbound.orders.cancel` + `hub.connect` appear in `PERMISSION_KEYS` even though no UI surface uses them today. `RolePermissionsEditor`'s Picker / Dispatcher columns will show toggles for those keys — that is the intended shape. A future `CancelOrder` action attachment should require no admin.ts update; the catalog is forward-compatible.

- **KTD3 — Per-button gating uses `usePerm` (reactive) as the default; `hasPerm` (snapshot) is reserved for non-React contexts (route loaders, network interceptors).** Doc review (Feasibility + Adversarial reviewers, confidence 75 cross-persona) verified that production Inventory + Orders components do NOT currently subscribe to `useAuth`, so a `hasPerm`-only gate would NOT re-render when perm[] changes mid-session (e.g., admin revokes a key on another tab; refresh-token rotation issues a narrower claim) — buttons stay visible until an unrelated state-change rerender. `usePerm` subscribes via `useAuth((s) => s.user)`, which is a single Zustand selector per component — referentially-stable and cheap; the prior "avoids redundant re-render loops" worry was overstated. Sprint-9.5 KTD12's fail-closed contract carries through either hook.

- **KTD4 — TenantHub policy change drops the bare `[Authorize]`.** Replace with `[Authorize(Policy = PermissionKeys.HubConnect)]` (single-line attribute swap). The policy inherits `RequireAuthenticatedUser()` from `AddShopFlowPermissionPolicies` so authentication remains enforced. Pattern matches Sprint-10 KTD5: per-action / per-hub policies are the single canonical gate; the bare `[Authorize]` is not belt-and-braces.

- **KTD5 — 33 403 tests live per-module in `tests/ShopFlow.<Module>.IntegrationTests/Authorization/<Module>403Tests.cs`.** Mirrors Sprint-10 U1-U4 reflection-test placement (per AGENTS.md §81 "test layout mirrors source"). CI per-csproj matrix surfaces drift earlier than a single cross-cutting test would.

### Deferred to Sprint-10.5 sign-off / future sprint (from doc-review)

- **[SEC-002][Hub revocation lag]** Hub.connect policy fires at negotiate time only; a user whose `perm[]` loses `hub.connect` mid-connection (e.g., role-permission revoked on another tab) continues receiving real-time push events until the JWT expires (15-min TTL). Accepted trade-off for Sprint-10.5 — within-tenant data exposure to a user whose access was explicitly revoked is bounded to the JWT window. Mitigations available but out-of-scope: (a) short-TTL JWT (already in place); (b) server-side forced-disconnect on role-permission update (`IHubContext.Clients.User(...).AbortAsync()` tracking connected sessions); (c) negotiate-on-every-reconnect with fresh token + perm[] check (`accessTokenFactory` already does this). Document the 15-min revocation lag as a known limitation in U6 sign-off trade-offs.
- **[KTD9 / adv-5][Version bump shape]** Patch (`v0.14.1-sprint-10.5`) vs minor (`v0.15.0-sprint-10.5`). The `hub.connect` attachment is a behavioral change to the auth contract — legacy tenants without `RolePermissionsSeed` re-run would break (SEC-001). Patch implies non-breaking; the SEC-001 unseed-path argues the change behaves as breaking for some tenants. Decision deferred to U6 sign-off when the SEC-001 mitigation is concretely landed: if a reseed step is part of Sprint-10.5 deployment, patch fits; if reseed is operator-runbook-only and any tenant might be missed, bump to minor.

Each of these is execution-time discovery or a sign-off-time decision — answerable by reading code, running grep, or weighing the deployment-readiness signal at U6, not by additional planning research.
